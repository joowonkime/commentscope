# 관점 비교·질의 백엔드 실행 가이드

2026-10-23 사용자의 진행 지시 및 일반 실패 시 휴먼루프 없이 자율 진행 지시를 적용한다.
사용자가 기존 r5 Goal을 clear한 뒤 새 objective를 실제 등록·active 확인했다. 등록 기록은 `runs/compare-backend-20261023-v1/platform-goal-start.json`이다. 기존 구현·실험·ledger는 보존했다.

## 현재 검증 결과

2026-10-23 실제2 Agent/각3 canonical 지지·집계6원문/최종2내용/실제6응답 검토·HTTP3라운드6응답 검증 완료. 정확한 산출물과 재현 명령은 [전달 자료](COMPARE_BACKEND_DELIVERY.md). 전체r5/전체UI/참가자테스트 완료는 아니다.

## 완료할 경로

기존 영상 하나의 댓글에서 관점 Agent를 자동 생성하고,
초기 의견 저장→두 관점 선택→같은 질문→입장·이유·조건과 원문 근거 확인을 프론트가 호출할 수 있게 한다.
조원들이 만든 Figma의 비교·대화·성찰 화면은 보존한다. 이번 백엔드 경로 완료를 전체 UI·사용자 테스트 완료로 보고하지 않는다.

## 완료 증거

- 실제 댓글 기반 서로 다른 Agent 최소2개, 각 유효 canonical 지지 최소3개. 이름만 다른 중복 Agent는 별개 관점으로 세지 않는다.
- 모든 집계 지지와 생성 Agent의 내용·필수 이유·조건·사실을 검토한다. 오류·미검토 승인0, 부모 이유 차용·조건 손실·입장 반전0.
- 고정 사실40건은 지원 승인≥8/10, 비지원 오승인0/30. 실제 Agent의 필수 사실은 별도로 검사한다.
- 각 Agent 실제3질문: 입장, 이유/조건 또는 후속 질문, 근거 밖 질문. 같은 질문에 자기 근거로 응답하고 자기 인용·적절한 보류·이력 분리를 확인한다. 전부 보류한 결과로 완료하지 않는다.
- 실제 HTTP 세션 생성·초기 의견 저장·관점 선택·질문/결과 조회·근거 조회를 재현한다. 입력 의견은 댓글 근거나 검증된 사실로 승격하지 않는다.
- 입력/코드/모델/검토 기록에 결합된 Agent 팩, API 계약, 실행 명령, 원문별 지지·보류 현황을 인계한다.
- 합성 fixture·수동으로 고친 관점 팩은 실제 자동 생성 성공의 증거로 사용하지 않는다. 기계 회귀와 의미 품질을 따로 보고한다.

## 입력과 경계

- 기존 UBI 고정 snapshot을 사용한다. 첫 개발 실험은 기존 개발 노출96개 전체로 시작하며 별도 namespace에 새 plan을 동결한다.
- 최초 개발 source IDs 정본: `runs/minimal-factory-r5-g3-20261018-v1/plan.json`의 `scope_ids`. 필요한 관점·지지의 가능성을 기존 자료로 먼저 점검한다. 입력 확대가 꼭 필요하면 같은 snapshot 안에서 이유·범위를 사전에 다시 동결한다. 원문을 바꾸거나 성공한 원문만 사후 선택하지 않는다.
- 이96개는 독립 새 G3가 아니다. 이번 완료를 기존 r5의 G3/G4 또는453/755 통과로 보고하지 않는다. 기존 r5 조건·실패·평가는 보존한다.
- Figma의 AI 일자리 문구는 예시다. 이번에는 기존 UBI 자료로 기술 경로를 검증하며, 화면 문구나 시연 영상 교체는 사용자와 먼저 논의한다.
- 기존 Qwen3-8B/GPU/thinking off 및 ledger를 재사용한다. 새로운 모델·유료 API·추가 GPT 실험·누적 총량 예산을 도입하지 않는다.
- 일반 코드·알고리즘·프롬프트 수정은 자율 진행한다. Figma 원본 편집·삭제·이동은 변경 항목과 이유를 사용자와 먼저 합의한다.

## 모듈 경계와 조원 공유

M0~M3는 완료를 확인하는 단계다. 코드의 분담 경계는 아래와 같으며, 현재는 같은 Python 프로젝트 안의 모듈이다. 별도 서비스나 독립 설치 패키지로 분리한 상태는 아니다.

| 분담 영역 | 현재 코드 | 전달하는 입력·출력 | 현재 상태 |
| --- | --- | --- | --- |
| Factory: 댓글에서 관점·자기 근거 구성 | `src/commentscope/factory/source_closed_policy.py`, `minimal_agents.py` | 고정 댓글 snapshot → 원문·주장·관계·사실 검증을 담은 bundle | 실제 compiled Agent2개·각 직접 검토 유효 지지3개. 전수 내용 검토 완료 |
| Agent 입력·응답 | `src/commentscope/agents/grounded_inputs.py`, `grounded_runtime.py` | bundle → `compile_inputs()`의 profiles → 선택 Agent별 질문·인용·보류 | 실제2 Agent·각3질문/인용/적절한 보류/이력 분리 검증 완료 |
| HTTP·세션 | `src/commentscope/agents/grounded_web.py` | bundle을 로드하여 세션·관점 선택·질문·상태·원문 조회 제공 | 실제 bundle HTTP3라운드6응답·초기 의견/세션/원문/부모 검증 완료 |
| 프론트 | 현재 로컬 참고 화면 `grounded.html`, `grounded.js`; 조원의 프론트는 별도 | [API 계약](COMPARE_BACKEND_API.md)의 JSON 요청·응답 | API를 기준으로 화면·연동 작업 분담 가능. 조원 Figma는 읽기 전용 |

Factory를 프론트의 매 질문마다 다시 실행하는 구조는 아니다. Factory가 만든 bundle을 HTTP 서버와 runtime이 로드해 사용하므로, 프론트 담당자는 Factory 내부 알고리즘을 구현할 필요가 없다. 모델 응답 실행에는 기존 Qwen 환경이 필요하다.

Factory→runtime 전달 경계의 정본은 `grounded_inputs.compile_inputs(bundle)`이다. 필수 필드는 `expires_at`, `sources`, `claims`, `relations`, `documents`, `checks`, `candidates`, `model`이며, `runtime_scopes`와 `source_contexts`는 선택 필드다. 구조 검사 통과는 Agent의 의미 품질 승인과 별개다. 원문별·Agent별 검토 기록은 모델 입력에 섞지 않고 실제 실행 승인에 별도로 결합한다.

지금 공유할 자료는 이 분담표, [API 계약](COMPARE_BACKEND_API.md), [사용자 테스트 과업 초안](COMPARE_BACKEND_USER_TEST_TASKS.md)이다. 검토된 실제2 Agent bundle과 실제 HTTP 재현 명령은 [전달 자료](COMPARE_BACKEND_DELIVERY.md)에 있다. 형식 예시·모의 응답은 실제 검증 결과로 세지 않는다. 현재 API는 같은 origin 사용을 전제로 하므로 별도 프론트 개발 서버는 프록시 등 연결 설정이 필요하다.

## 작업 순서

| 단계 | 작업 | 종료 증거 |
| --- | --- | --- |
| M0 | 기존 grounded HTTP API 재사용, 초기 의견 저장·세션 분리 | HTTP·저장·근거 비혼입 회귀 통과. 실제 Agent 품질 통과로 세지 않음 |
| M1 | Factory 산출물→현재 runtime 연결 및 공통 입장/출처별 이유 경계 구현 | 사전에 확대·동결한 실제999개 범위에서 Agent 수·지지·오류·미판정·누락 비교 |
| M2 | 생성 지지·Agent·사실 전수 검토와 실제 runtime | 최소2 Agent와 실제6응답의 근거·보류·이력 검사 |
| M3 | 실제 산출물로 HTTP 경로 재현 및 사용자 테스트 과업 문서 | 프론트가 호출 가능한 입출력·재현 명령·검토 기록 |

M1 전에 새 가설·입력·호출/코드/모델·평가표를 동결한다. 기존 중단 G3 plan을 그대로 재시작하지 않는다.
완료한 기계 작업과 의미 품질 실험을 같은 사이클 수로 부풀리지 않는다.

## 사이클 규칙 — 승인 대기 없이 진행

1. 매 제품 실험 전 현재 제품 병목 하나, 변경 하나, 예상 개선 지표와 실패 기준을 적는다.
2. 지표는 후보 보존, 유효 공유군집, 실제 Agent 수/지지, 오가입·이유 귀속·조건 오류, 실제 응답 성공 수다. 국소 프롬프트 정답률만으로 제품 개선을 선언하지 않는다.
3. 실행 뒤 이전 대비 값·원문 사례·채택 여부·다음 동작을 해당 run에 저장하고 짧게 보고한다. 일반 실패·단계 전환 때 재승인을 묻지 않는다.
4. 같은 병목에서3회 연속 제품 지표 개선이 없으면 인과와 구조를 재검토해 다른 접근으로 전환한다. 휴먼루프를 자동으로 만들거나 승인 대기를 추가하지 않는다.
5. transport 재시도0·기존 자원 보호 유지. 불명확한 요청은 재발송하지 않는다. 실패를 지우거나 기준을 바꿔 통과시키지 않는다.
6. 첫 미완료 단계부터 진행하고, 파일·원문·기존 기록을 다시 전부 읽는 복원 루프를 만들지 않는다.

## 허탕을 줄이는 실행 전 판단

- 새 추론 전에 기존 실패로 무엇이 이미 판별됐는지, 이번 결과가 어떤 구현 선택을 바꿀지 기록한다. 이전과 같은 가설·원인·측정이면 새 호출을 만들지 않는다.
- 변하지 않은 요청은 ledger 결합을 검증한 정확 캐시를 우선한다. 코드로 확인할 수 있는 인용·출처·중복·연결·용량 문제를 의미 모델에 다시 묻지 않는다.
- 본 실험 전에 입력에 필요한 관점·지지가 존재할 가능성과 최종 runtime 연결을 확인한다. 불가능한 표본·깨진 연결로 대규모 추론하지 않는다.
- 예상 호출·입력 토큰·판별할 가설을 먼저 적고 필요한 차이만 실행한다. 새 누적 총량 예산을 설정하는 의미는 아니다.
- 국소 진단이 좋아져도 공유군집·유효 Agent·실제 답변에 연결되지 않았다면 제품 개선0으로 기록한다. 이미 반증된 접근은3회를 채우지 않고 배제한다.
- 원문·응답·거대한 도구 목록을 반복 출력하지 않는다. 전수 검토는 ID별 저장과 미검토 큐로 이어가고 필요한 차이만 대화에 올린다.

## 사용량과 플랫폼 Goal

- 주간 잔여량 **40% 이하 감지 즉시** 구현·추론·의미 평가를 멈추고 정리·checkpoint·실제 Goal pause만 수행한다. 현재 사이클 완료 예외는 없다.
- 새 사이클 전·각 실행/도구 묶음 전·진행 중 최대60초 간격으로 기존 `account_quota_guard.py`를 확인한다. 오래되거나 없는 메타데이터에서는 새 작업을 시작하지 않는다.
- 이 가드는 계정 관측 기반 작업 제어다. 계정의 네이티브 사용량 상한은 아니며 메타데이터 지연 가능성을 기록한다.
- 10월23일 사용자가 명시적으로 진행을 지시해 과거 latch를 감사 기록과 함께 해제했다. 과거40% 중단 기록은 `runs/compare-backend-20261023-v1/quota-before-resume.json`에 보존했다.
- 새 Goal은 `runs/compare-backend-20261023-v1/objective.txt` 본문과 정확히 일치하며 실제 active다. 기존 r5는 미완료 후속 기준으로 보존한다.
- 새 모델 실험 전에도 quota와 동결 계획을 확인한다. 일반 실패에 재승인 대기를 만들지 않고 첫 미완료 단계부터 진행한다.
