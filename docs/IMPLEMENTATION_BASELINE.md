# 구현 AI가 따를 구조와 설계 확정 경계

2026-11-19 / TASK-030 / REQ-009·010. 사용자가 요청한 임의 구조 결정 방지 지침이다.
이 문서는 현재 구현의 보존 기준과 설계 결정 절차다. 미구현 기능의 최종 아키텍처를
새로 확정하는 문서가 아니며, 과거 설계 제안을 전부 채택하지 않는다.

## 1. 구현 Issue는 확정된 계약에서 시작한다

구현 담당 AI는 다음 항목을 Issue에서 확인한다.

1. 관련 TASK/REQ/DEC와 적용할 설계 문서의 절·기준 commit 또는 PR.
2. 현재 구현 보존인지, 이미 수락된 확장 계약의 구현인지.
3. 이번 책임·입출력·상태·오류·수정 대상과 완료 조건.
4. 구조/정책 변경이 있다면 사용자 또는 명시적으로 설계 권한을 위임받은 팀 담당자의
   수락 근거. 기존 대화·결정에 수락이 있으면 그 근거를 연결하고 재확인을 요구하지 않는다.

현재 동작 보존과 수락된 계약 안의 버그 수정·함수 분리·화면 조정·관련 검사에는
새 구조 승인이나 매번의 사람 확인이 필요하지 않다.
Issue 번호, 설계 문서 작성, 설계 PR 생성·CI 성공만으로 새 구조를 수락한 것이 되지 않는다.
구현 AI가 자기 제안을 작성한 뒤 스스로 수락 처리하지 않는다.

## 2. 현재 구현의 보존 기준

기준 코드는 main `6c825812cddc09b708d6f7f7ebe98875ba42f726`이다.
책임과 호출 경로는 [현재 구조](design/IMPLEMENTED_STRUCTURE.md), 실제 제품 계약은
[PRODUCT_API](PRODUCT_API.md), 1출처/논거 확장 정책은
[DEC-028 계약](design/SEEDED_PERSPECTIVE_DEBATE.md)을 함께 따른다.
다음은 보존할 기존 경계이며 최종 서비스 설계의 품질 인증이나 영구 고정을 뜻하지 않는다.

| 기준 | 현재 경계 | 구현 담당자가 임의로 바꾸지 않을 결정 |
| --- | --- | --- |
| B-01 생성/대화 분리 | snapshot → Factory → 불변 bundle → 제품 Analysis/Runtime | 질문마다 Factory를 재실행하거나 댓글에서 근거 없는 persona를 직접 합성 |
| B-02 원문/관점 | 자기 원문·parent·ID·조건·지지 보존, 명시된 새1출처와 legacy 정책 구분 | 최소지지·대표성·허용 근거·미평가/반대의 의미 변경 |
| B-03 발언 생성 | SeededSession이 자기 관점/근거·문맥으로 생성, 별도 관측과 Host 검사를 적용 | 생성/판정 역할·출처 origin을 합치거나 상대 발언을 검증 사실/댓글 지지로 승격 |
| B-04 대화 제어 | ProductApp Controller가 순서·job·중단/개입과 실행 한도 관리 | Agent가 자율적으로 다른 Agent/도구를 호출하는 새 실행 방식 |
| B-05 제품 연결 | 기존 `/api/v1`·revision/idempotency·job 조회·출처 API와 기존 화면 | 프론트가 별도 Agent 생성/검증을 수행하거나 독립 API/ID/상태를 정의 |
| B-06 저장/비용 | 불변 분석, 개인 의견/대화/성찰 DB, 공유 금융장부 구분 | 원 bundle 덮어쓰기·출처/사용자 데이터 혼합·기존 비용/기한 초기화 |

모델·프롬프트·배정은 해당 실행의 동결 설정을 따른다. 위 역할 이름은 모델을 영구 채택하거나
역할마다 별도 서비스·LLM 호출을 추가하라는 뜻이 아니다.
알려진 1000 기본값 전달 결함이나 답변 품질 실패는 보존할 제품 요구사항이 아니다.
기존에 명시된 용량·응답 계약 안의 수정을 맡은 경우 그 결함을 재현하고 고친다.
새 무제한 용량이나 다른 지지/판정 정책을 결함 수정에 끼워 넣지 않는다.

## 3. 미래 기능은 아직 구현용 설계가 모두 확정되지 않았다

토론·합의·통합 Agent는 [DS-v1 상세 설계안](design/DEBATE_SYNTHESIS.md)으로 구체화했다.
DEC-029는 proposed이며 사용자/위임 담당자의 수락 전 구현 기준으로 자가 확정하지 않는다.
아래 토론/통합 행은 상세안의 선택 DS-01~10을 검토할 대상이다.

| 대상 | 확정되지 않은 구현 결정 | 구현 전 필요한 상세 계약 |
| --- | --- | --- |
| 쟁점 중심 debate | 반박 대상/쟁점 표현, 수용·입장 변화 여부, 종료 판단 | 상태·메시지 자료형·문맥 선택·Controller/Runtime 책임·정상/실패 사례 |
| 합의·통합 Agent | 합의 기준, 이견 유지 방식, 새 Agent 자격과 계보 | 입력/출력·원문/AI/문헌 출처·새 Compiler 경계·저장·API·검증 |
| 홈·URL·개인 기록 | URL 요청/준비 영상 재사용, 분석 대기, 기록 수명과 복원 | 화면/API 대응·job·권한·실패/재사용·운영/비용 계약 |
| 최종 Figma 연결 | 최종 화면·통합 기능의 사용자 흐름 | 확정 화면과 기존/신규 API 대응·대기/보류/오류·동작 확인 |

기존 구조 문서, 협업 분담 예시, 과거 대화의 후보 설명은 위 항목의 상세 확정 설계를
대체하지 않는다. 반대로 이미 명시적으로 확정된 부분까지 다시 미결정으로 만들지 않는다.

## 4. 필요한 구조가 비어 있을 때

구현 담당 AI는 빈 부분을 추측해 새 구조로 코딩하지 않는다. 다음 내용의 설계 변경안을
문서/설계 PR로 먼저 정리한다.

- 해결할 요구와 현재 구조로 처리하기 어려운 구체적 사례.
- 유지할 경계, 대안·선택 이유, 역할/모듈 책임과 의존 방향.
- 요청/응답·자료형·상태·오류·저장·원문/출처 연결의 상세 계약.
- 정상/부정 예시, 기존 자료/API 호환과 전환, 비용·속도·검증 영향.
- 미결정 목록과 수락 근거를 기록할 위치.

사용자 또는 위임된 설계 담당자가 내용을 수락하면 문서·관련 DEC·계약 참조를 맞춘다.
그 뒤 작업을 나눠 구현한다. 그동안 이미 계약이 있는 독립 작업·합성 확인·관련 버그 수정은
계속할 수 있다. 구조 변경안 작성이 새 모델 실행·Figma 변경 권한을 만들지는 않는다.

## 5. PR에서 확인할 것

구현 PR은 적용한 설계/절·기준 revision, 계약 변경 유무와 수락 근거, 호환성·검사·미검증을
적는다. 구조 변경안과 구현을 한 AI가 동시에 자가 확정해 제출하지 않는다.
기존 계약 안의 수정은 변경 없음과 해당 계약 참조를 적으면 된다.

현재 이 절차는 AI 지침·Issue/PR 검토 규칙이다. CI가 의미를 읽어 모든 구조 변경을
자동 차단하는 기능이나 GitHub의 추가 사람 승인 규칙을 새로 설정한 것은 아니다.
