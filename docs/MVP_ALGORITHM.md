# 시연 MVP 알고리즘과 모듈별 책임

이 문서는 [제품 정책](MVP_PRODUCT_POLICY.md)을 구현할 실행 구조와 작업 순서를 정한다.
정책은 허용할 결과와 평가 기준이고, 알고리즘은 그 결과를 만드는 절차다. 프롬프트는 모델 호출의 인터페이스이며 이 둘의 대체물이 아니다.
최신 제품 경로 검증은 **자동 입력2개 전체의 실제 질문·비교·출처 흐름**까지 완료했다.
`argument_graph_probe` 용량 비교 뒤 분석 프롬프트를 고정하고 `actual_agent_probe`로 답변20/20·보류20/20,
비교 P95 13.72초와 브라우저 흐름을 확인했다. 입력의 미해결 의미 품질과 답변·UI 성능은 분리하며, 좋은2개를 수동 선별하지 않았다.
최신 fresh 통합 실행은50분6초·최종 입력1개다. 다음 Goal 작업은 원문 지지 범위·주요 사실 누락을 현행 정책에 따라
판정할 경계와,1시간 안에 충분한 서로 다른 관점을 확보하는 예산 배분이다.
전자는 원문별 지지·이유 소유권·필수 사실의 연결을 다루며, 관점 수를 맞추기 위한 실패 사실 삭제나 사례별 문구 예외를 추가하지 않는다.
후자는 기존 단계 산출물 인터페이스를 연결해 snapshot부터 측정하며 cached 진단 시간을 합쳐 fresh 성공으로 대신하지 않는다.
이전 **주장과 이유 연결을 보존하는 입력 구성**은 다음과 같다. 오류별 판정기를 계속 추가하는 작업보다
서로 다른 실제 Agent 2개와 질문·출처 확인으로 이어지는 전체 경로의 병목을 우선한다. 합격 정책을 완화하지 않는다.
fresh runner 0.3에 첫 source-first 기준선을 연결했다. 실제 실행은39분21초에 완료됐지만 최종 입력0개로 제품 기준에 미달했다.
[실제 결과와 다음 교체 경계](MVP_ACCEPTANCE_STATUS.md#source-first-실제-통합-결과)를 따른다. 새로운 알고리즘의 우월성을 주장하지 않는다.

## 주장과 이유 연결을 보존하는 입력 구성

### Snapshot부터 실행하는 통합 경로

`experiments/fresh_product_pipeline.py`는 기존 단계들을 새 snapshot에서 한 번에 실행한다.
이전 fresh·graph 계획에서 모델·배포·판정 정책·사실 자료·예산 설정만 명시적으로 가져온다.
과거 추출 단위·임베딩·판정 응답·후보 선택·개발 검토는 실행 입력으로 재사용하지 않는다.

1. snapshot 전체의 canonical 원문을 새로 임베딩하고 기존20개 검색 묶음의 고정 순서대로 원문을 분석한다.
   runner0.2는 원문 분석 배분2100초와 미처리·실패 구분을 사용한다.1000개 전부를 의미 분석했다고 표시하지 않는다.
2. 추출 단위를 새로 임베딩해 frame 내부 medoid·NLI 대안과 frame을 넘는 의미 이웃을 함께 탐색한다.
   기존 임계값·모델·프롬프트는 유지한다. NLI는 후보 검색이지 가입 승인이 아니다.
3. 최소 지지에 도달할 수 없는 core만 아래 상한 규칙으로 중단하고, 나머지 예정 관계를 모두 검사한다.
   기존 medoid/대안 중 지지가 많은 쪽을 택한다. 동일한 핵심 계약만 합쳐
   canonical 원문을 한 번씩 센다. 의미 유사성에 의한 새 합의 문장 생성·반대 관점 병합은 하지 않는다.
4. 모델 지지3개 이상 후보를 지지 수·ID 순으로 최대6개 profile에 배분한다. 예산 밖 후보를 기록하며,
   유형·사실 성공 여부나 개발 평가를 보고 좋은 후보만 고르지 않는다. 노출되는 모든 입력은 평가 대상이다.
5. 기존 graph의 근거 선택·독립 유형 판정·이유 지지·필수 근거 보류·사실 검사·입력 조립을 실행한다.
   핵심·이유 단계의 완전히 동일한 요청은 이 실행 안에서만 재사용한다. 오류도 재사용하며 다시 추론하지 않는다.

전체3600초 deadline에는 무결성 검사·모델 적재·새 임베딩·모든 추론을 포함한다. 기존8시간 ledger를 유지한다.
profile은8192/1024, membership은4096/256, 추출은 기존non-thinking 설정이다.
GPU 배치는 준비 시 `all` 또는 `32`를 명시하고 고정한다. 자동 메모리 fallback이나 새 모델 다운로드는 없다.
`all`은 이전 fresh 실행에 사용된 배치이며 이번 전체 실행은 deployment 차이를 포함한 통합 검사이지 prompt 단독 비교가 아니다.

이 경로의 synthetic 통합 검사는 원문부터2개 입력까지 연결되더라도 `qualified_agents=0`과 품질 미승인을 유지한다.
실제 fresh 결과·전체 내용 검토·질의/UI 검사를 마치기 전 기본 승인 경로로 승격하지 않는다.

### 최소 지지 상한을 이용한 예산 배분

`core_admission_bound.py`는 모든 검색 경로의 **완전히 같은 핵심 계약**에 연결된 canonical 원문을 먼저 집계한다.
현재 판정된 지지를`s`, 아직 평가하지 않은 원문을`u`라 할 때`s + u < 3`이면 나머지가 전부 지지여도 채택될 수 없다.
그때만 추가 모델 요청을 생략한다. 검색 경로별로 따로 중단하면 다른 경로의 지지를 놓치므로 전체 예정 집합으로 상한을 계산한다.

생략은`unassessed`로 남고 비지지로 바뀌지 않는다. 생략 이후에도 그 원문은 상한의 가능한 지지로 유지한다.
이미 받은 동일 요청 결과는 재사용하며 오류를 재시도하지 않는다. 반대로 지지3개를 찾았다는 이유로 일찍 성공 처리하지는 않는다.
채택 가능한 핵심은 남은 원문도 전부 검사하므로 최종 지지 수를 낮은 추정치로 대체하지 않는다.
탈락 후보의 미완료 지지 수에는 완전성 표시와 최대 가능 지지를 함께 기록한다. 의미 판단·찬반 병합·지지 기준 완화는 하지 않는다.

fresh0.1의 모든 판정을 재생한 개발 비교에서 core 요청75회 중24회를 생략했고 최종 채택 후보·원문·지지 수가 같았다.
해당24호출의 과거 청구시간은244.21초지만 실제 새 실행의 절약 시간은 아직 아니다.
runner0.2는 이 변경과 원문 추출 배분1800→2100초를 함께 검증한다. 전체3600초와 누적8시간은 그대로다.
추출 순서·검색 임계값·모델·prompt·schema·사실 정책은 유지한다. 추가 처리될 특정 원문을 사람이 선정하지 않는다.
이것은 계산 배분의 통합 비교이며 단일 요소의 정확도 개선이나2개 관점 확보를 미리 주장하지 않는다.

### 이전 근거 선택 구조

직전 제품 경로 검사는 최종 입력0개였다. 이유 인용만 재사용하면 그 인용이 원래 설명하던 주장과의 연결이 사라지므로,
`argument_graph`는 원문 ClaimUnit의 주장 인용·이유 인용을 각각 node로 만들고 원래 방향을 link로 보존한다.
주장 인용도 다른 관점의 이유가 될 수 있지만, 그 관계는 원문에 있어야 하며 모델이 새 논거를 만들어서는 안 된다.
node와 link가 원문에 결합됐다는 것은 추출의 의미가 맞다는 승인이 아니다.

이번 변경은 한 호출이 선택·유형·의존성을 모두 결정하던 구조를 나눈다.

1. 공통 입장의 유형을 별도 단일 enum으로 판정한다. 원문·입장 문장은 수정하지 않는다.
2. 원래 주장–이유 연결과 지지 원문 전체를 보고 주요 근거 node 최대2개와 필수 근거를 선택한다. 이 단계는 유형을 출력하지 않는다.
3. 선택된 각 구간의 사실/가치/예측/혼합·불명 유형을 독립 호출로 판정한다. 이전 유형이나 사실 검사 결과를 입력으로 주지 않는다.
4. 코드는 선택된 원문을 그대로 복사하고, 사실로 판정된 필수 근거의 의존성을 유지한다. 혼합·불명은 후보 전체를 보류한다.
5. 기존 원문 지지·외부 사실 검사·입력 조립을 수행한다. 필수 근거는 예측이어도 원문 지지가 없으면 후보 전체를 보류한다.
   일부 이유를 삭제하고 같은 후보를 통과시키는 처리는 하지 않는다.

외부 검증이 불가능한 개인 경험을 미검증 증언으로 허용하는 정책은 변경하지 않았다.
유형을 바꾸는 것은 새 독립 모델 판단의 검증 대상이지, 실패한 사실을 우회하기 위한 코드 매핑이 아니다.
이미 읽은 실패 사례에 대한 개발 실험이므로 독립 검증 성능으로 보고하지 않는다.

두 후보 검색 경로의 모델 지지3개 이상 후보를 합쳐 **전부** 검사한다. 기존 strict-frame/NLI-target 경로3개와
semantic-neighborhood 경로2개이며, 후보 ID·원문·핵심·모든 가입 판정(부분·비지지 포함)을 보존한다.
수동으로 좋은 후보만 남기거나 의미가 같다고 임의 병합하지 않는다. 실제 노출될 전체 입력에서 구별되는 관점과 오류를 평가한다.

`experiments/argument_graph_probe.py`는 두 경로의 원시 membership과 순위를 재생한 뒤 새 계획을 동결한다.
`ranked-provenance`는 기존 verifier를 재사용한 준비 전용 manifest이며, 또 하나의 모델 실행이 아니다.
고정8개 합성 유형 통제는 진단용이고 실제 Agent 검토나 기존 사실40건을 대체하지 않는다. 통제 정답은 모델 요청에 넣지 않는다.
기존8시간 ledger, cached 실행1800초, 재시도0, 이유 관계최대40을 유지한다.
이번 계획의 실제 후보는5개, 이유 관계 상한38개다. 실험 성공과 fresh1시간·실제 질문·UI 통과는 별도로 확인한다.

첫 실행은 유형 통제8/8·자동 입력3개를 얻었지만 내용 검토 통과0개였다. 주장의 재진술이 이유로 선택되는 문제가 남았다.
또한 한 선택 요청은 입력3915토큰으로4096문맥의 거의 전부를 사용했고 답변 없이 길이 제한에 도달했다.
256토큰 판단 예산에 걸린 다른 사례도 있어, 후속0.2는 지시문·schema·후보를 유지한 **용량 설정 비교**를 지원한다.
`baseline`은4096문맥/256판단토큰, `expanded`는8192/1024이며 생성 상한을 각각768토큰 늘린다.
이 증가는 profile 단계에만 적용한다. 원문/이유 가입 판정은 기존 설정을 쓰는 별도 순차 서버에서 실행한다.
서버를 동시에 적재하지 않으며 모든 시간과 비용은 동일 deadline/ledger에 합산한다. 더 긴 판단이 의미 품질을 개선한다고 미리 결론 내리지 않는다.

## 제품 경로 중심 사이클

2026년 10월 14일 사용자 지시에 따라 개별 오류마다 검사기를 추가하는 접근을 보류했다.
직전 실행은 입력1개를 조립했지만 유의미한 이유가 없어 내용 검토 통과 Agent는0개였다.
독립적인 이유 역할 검사만 추가하면 이를 더 잘 거절할 수는 있어도 사용할 Agent가 늘어나지는 않는다.
그 검사 초안은 채택하지 않았으며 실제 모델 호출도 하지 않았다.

이번 `product_path_probe`는 기존190개 원문 분석에서 나온215개 단위와 임베딩을 재사용한다.
추출 대상과 출력 문장을 손으로 바꾸지 않고 다음 두 경계를 함께 교체한다. 따라서 단일 변경의 인과 효과를 주장하는 ablation은 아니다.

1. **후보 검색과 가입 분리:** 정확한 scope·modality·stance·target 문자열 bucket 대신 각 기존 단위에
   cosine 유사도0.55 이상인 다른 canonical 출처 최대4개를 검색한다. 같은 출처의 중복 단위는 한 번만 센다.
   기존 NLI는 target별 다른 출처2개 이상의 추정 지원과 점수 합으로 순위만 정한다. 최종 지지 수는 기존 full-source membership으로 다시 결정한다.
   최대250단위·1000 NLI쌍·6후보이며, 검색 출처 집합 Jaccard가0.6을 넘는 후보는 검색 다양성 예산으로 보류한다.
   이 보류는 두 관점이 같다는 판정이 아니다. 개인/일반·조건·입장 차이를 합친 새 주장은 생성하지 않는다.
2. **이유 추출 결과 재사용:** 임의의 모든 연속 문장 구간 대신, 지지 원문에서 이미 추출한 `reason_quote` 전체를 ID 메뉴로 제공한다.
   원문 전체도 함께 주며 관련 이유 선택·유형·필수 사실 선언은 여전히 모델 판단이다. 출처가 다르거나 원문에 없는 구간은 코드로 거절한다.
   메뉴에 필수 전제가 없으면 보류한다. 형식적으로 올바른 인용을 유효한 논거로 간주하지 않으며, 주요 사실 검사와 의존성 정책은 유지한다.

선정한 후보 전부에 가입→typing→이유별 지지→사실→입력 조립을 실행한다. 실행 전 코드·입력·모델·배포·요청 한도를 고정한다.
기존8시간 ledger를 그대로 사용하고 이번 cached 실행 상한은1800초, 재시도0이다. 새 다운로드·유료 API·웹 검색은 필요하지 않다.
실제 Agent 수, 탈락 단계, 원문 보존, 비용으로 평가하며 테스트 통과나 거절 수 증가만으로 제품 진전을 주장하지 않는다.

자동 조립된 입력 **전체**의 핵심·이유·필수 전제 누락·서로 다른 관점 여부를 개발 평가한다.
왜곡 없이 구분되는 Agent2개 이상이면 실제 질문·보류·비교·출처 UI 검사로 이어간다. 독립 gold나 무인 서비스 품질 인증은 아니다.
미달이면 해당 사이클 결과와 병목을 기록하며 같은 출력에 프롬프트 예외를 덧붙여 재시도하지 않는다.
cached 성공과 fresh1시간 달성은 구분한다. 검증 전에는 기존 production 경로나 README의 완성 상태를 바꾸지 않는다.

구현 경계는 `factory/semantic_neighborhood.py`, `factory/unit_reason_typing.py`,
`experiments/product_path_probe.py`다. 기존 medoid·range typing과 과거 실행 기록은 비교 기준으로 보존한다.

실제 실행은14분35초에 완료됐지만 후보6개→지지3개 이상2개→최종 입력0개였다.
현재 조합은 제품 개선으로 채택하지 않는다. 두 이유가 원래 설명하던 주장과 새 core의 관계가 다르고,
예측의 사실 오분류가 남았다. 개인 경험의 외부 검증 불가도 별도 정책 제약이다.
다음 교체 경계는 원문 내 주장–이유 연결 보존과 유형 판정의 분리이며, 후보 검색 threshold를 다시 조정하는 작업이 아니다.
실행 기록과 비용은 [재개 지점](NEXT_SESSION.md#제품-목표-중심-통합-사이클-결과)에 있다.

## 네 가지 변경 경계

| 경계 | 결정할 일 | 변경 시 필요한 증거 |
|---|---|---|
| Policy | 관점 자격, 지지 집계, 사실 허용 범위, 제품 합격과 진단 목표 | 사용자 합의와 버전 있는 정책 기록 |
| Algorithm | 분석 순서, 후보 검색, 묶기·분리, 데이터 흐름, 실행 예산 | 같은 입력의 단계별 결과·비용·누락량 비교 |
| Model | 의미 추출·지지 판단·문서 근거 판정의 구현 | 고정 표본의 실제 출력과 오류 유형. JSON 성공만으로 의미 품질을 승인하지 않음 |
| Prompt | 모델이 수행할 단일 작업, schema와 입력 경계 | 모델·입력·평가를 유지한 별도 변경 실험. 개별 실패마다 지침을 추가하지 않음 |

출처·인용 위치·중복·허용 ID·시간·재시도는 코드로 통제한다. 의미적 호환성이나 필수 조건 여부를 코드가 완벽히 아는 것처럼 취급하지 않는다.
LLM을 없애는 대신 그 결정이 끼치는 범위를 제한하고, 원시 입력·출력과 후속 집계를 재현 가능하게 남긴다.

## 실행 기준선

```text
Snapshot + 원문 registry
  → 다국어 임베딩으로 분석 후보와 처리 순서 결정
  → 원문별 ClaimUnit 분석과 결과 저장
  → ClaimUnit의 의미 후보 검색·호환성 검사
  → CandidatePerspective
  → 공통 입장과 지지 관계·개별 이유·조건 차이
  → 주요 사실 검사와 입력 조립
  → PerspectiveSpec → 근거 제한 Agent → 비교 UI
```

기존 raw-group→대표 core→가입 경로는 비교 대상으로 보존한다. 새 기준선에서는 **가입시킬 대표 문장을 원문 분석 입력으로 주지 않는다**.
원문별 분석을 먼저 보존하고, 그 분석과 원문에서 후보와 설명을 만든다. 이는 새로 발견한 해결책이 아니라 초기 Factory 설계의 분리 원칙이다.
과거 source-only/V1 비교에서도 오류가 있었다. 처리 순서를 바꿨다는 이유만으로 의미 문제가 해결됐다고 간주하지 않는다.

### 원문과 후보 검색

- 기존 최대1000개 snapshot을 검증하고 canonical ID, 원문, parent 링크, 언어, 만료를 유지한다.
- 다국어 임베딩과 기존 cosine/average-linkage 구현을 후보 검색 기준선으로 재사용한다. 기존0.45는 출발 설정이지 검증된 최적값이 아니다.
- raw 묶음은 처리 순서와 후보 검색에만 사용한다. 묶음 크기·좋아요·유사도를 원문 지지로 간주하지 않는다.
- 처리 순서는 후보별 순환과 안정적인 ID 순서처럼 결과를 보기 전에 정한 방식으로 고정한다. 알고 있는 좋은 댓글을 손으로 고르지 않는다.
- 시간 때문에 분석하지 못한 원문은 `unprocessed_budget`로 남긴다. 무주장·반대·비실질 댓글로 재분류하지 않는다.
  모든 원문을 임베딩한 것과 모든 원문의 의미를 검사한 것을 구분해 표시한다.

### 원문별 분석

기존 `contracts/claims.py`의 ClaimUnit 계약을 출발점으로 삼는다. 입력은 대상 원문과 명시적으로 제공한 문맥이며,
다른 댓글의 대표 주장이나 평가 라벨을 넣지 않는다. 부모 원문을 사용한 결과는 own-comment-only 결과와 같은 조건의 점수로 비교하지 않는다.
기존 `claim_prompt.py`는 UBI 주제 전용이다. 이번 고정 영상의 기준선으로만 취급하며, 다른 영상에서는 주제 설정과 prompt 버전을
명시적으로 결합해야 한다. 영상 ID만 바꿔 동일한 의미 품질이 보장된다고 설명하지 않는다.

각 단위에는 주장·논점·입장 대상·입장·개인/집단 범위·양태·이유·조건과 원문 인용을 보존한다.
출처 ID와 claim ID는 코드가 부여한다. quote가 원문에 존재한다는 것은 문자열 계약 통과이지 정확한 해석의 증거는 아니다.
형식 오류, 원문에 없는 인용, 무주장, 문맥 부족, 호출 오류를 서로 다른 상태로 남긴다. 자동 문장 수리나 무제한 재질의는 하지 않는다.

원문별 결과는 source/context hash, 모델 hash, schema/prompt 버전과 실행 설정에 결합한다. 동일 조건의 후속 단계는 재사용한다.
첫 분석1시간을 측정하는 실행에서는 이전 분석 cache 시간을 새 분석 시간인 것처럼 보고하지 않는다.
기존 ClaimUnit 실험 경로의60-comment/300-unit 제한을 전역으로 해제하지 않았다.
새 adapter는 최대1000개 snapshot에서 큰 raw 묶음20개를 처리 후보로 고르고, 각 원문을 한 번씩 분석한다.
분석 단계는 전체 시작 시각 기준1800초 안에서 새 호출을 시작하며, 전체 실행은3600초 deadline을 공유한다.
원문 요청27000bytes, 출력1200tokens, 단위 후보 처리 최대6000개를 명시한다. 전체999개의 의미 분석을 보장하지 않는다.

### 묶기와 관계 결정

1. 단위 임베딩으로 가까운 후보만 검색한다. 모든 원문 쌍을 LLM으로 비교하지 않는다.
2. 같은 논점·입장 대상인지 먼저 확인한다. 서로 다른 대상을 향한 support/oppose enum만으로 합치거나 나누지 않는다.
3. 명시적으로 다른 작성자 범위·양태·중요한 조건을 하나의 무조건적 주장으로 합치지 않는다.
   그 차이가 중요한지는 아직 모델 판단과 평가가 필요한 부분이며 문자열 일치만으로 결정하지 않는다.
4. 후보마다 공통 입장과 세부 이유·조건을 별도 산출물로 만든다. 후보 이름은 탐색용 설명이지 모든 구성원의 지지 명제가 아니다.
5. 공통 주장에 대한 지지 수는 원문 관계에서, 각 이유의 수는 그 이유의 관계에서 따로 계산한다. 애매한 가입은 확정 수에 더하지 않는다.
6. 한 카드로 중요한 차이를 보존할 수 없으면 split/defer한다. split/merge 횟수와 결과 계보를 제한·기록하고 무한 재생성을 막는다.

최소3 canonical 지지는 필요조건이며 주류·인구 대표성·의미 정확성의 충분조건이 아니다.
중복 여부와 수의 집계는 코드 책임이지만, 그 댓글이 해당 주장을 지지하는지는 남아 있는 모델 결정이다.

첫 구현은 scope·modality·stance·정규화한 stance target이 같은 단위를 먼저 나누고,
각 묶음 안에서 cosine/average-linkage0.45를 적용한다. 모호한 frame은 보류한다.
이 엄격한 구분은 반대 입장 혼합을 줄이려는 후보 검색 가설이며, 같은 대상의 의역도 갈라놓을 수 있다.
조건의 의미적 동등성이나 군집 순도를 문자열 구분만으로 보장하지 않는다.

대표 후보는 이미 추출된 단위 중 medoid를 선택하며 새 공통 요약을 생성하지 않는다.
한 댓글에서 여러 단위가 나와도 대표 선택과 지지 집계에서 여러 사람처럼 가중하지 않는다.
선택된 문장은 합의가 아니라 검증할 target이다. 이후 기존 membership 모델이 각 원문 전체와 target의 지지 관계를 검사하고,
3개 이상 지지한 후보만 기존 typing·이유별 검사·사실 입력 조립으로 보낸다. 자동 반복 split/merge는 아직 구현하지 않았다.

현재 구현 경계는 `factory/source_first.py`(스케줄·원문 결합·후보 선택),
`providers/source_first_candidates.py`(로컬 단위 임베딩), `factory/product_evaluation.py`(평가 상태),
`experiments/fresh_grounded_pipeline.py`(실행·기록·예산)다. 기존 `claim_prompt.SYSTEM`과 schema를 그대로 사용한다.

### 사실과 Agent

Agent가 사용할 주요 사실과 필수 전제만 검사한다. 모든 댓글의 모든 문장을 외부 검색·팩트체크하지 않는다.
현재 합의대로 핵심 필수 사실 전제가 미검증이면 후보를 보류한다. 원문에 없는 논거를 외부 자료로 보충하지 않는다.

기존 `grounded_inputs`의 공통 입장·이유별 출처·의존성 제한과 `grounded_runtime`의 허용 claim ID 선택을 재사용한다.
자유롭게 설득문을 만든 뒤 같은 모델이 승인할 때까지 반복하는 구조로 바꾸지 않는다. 허용 근거에 없는 질문은 보류한다.
Agent의 공통 입장, 일부 구성원의 이유, 사실 근거, 불확실성은 화면과 답변에서 구분한다.

## 남아 있는 모델 판단

| 판단 | 코드가 보장할 수 있는 부분 | 실험으로 확인해야 하는 부분 |
|---|---|---|
| 원문 해석 | 입력·문맥·quote·ID 결합 | 풍자, 질문, 지시어, 주장 강도와 조건의 올바른 해석 |
| 관점 형성과 가입 | 후보 범위·중복·관계 이력·집계 | 실제 공통 입장, 중요한 내부 차이, 지지 여부 |
| 유형과 주요 이유 선택 | 선택한 원문 구간의 위치·내용, 선언된 필수 사실 의존성 보존 | 사실/가치/예측 구분, 이유의 관련성, 선택하지 않은 필수 전제의 누락 여부 |
| 주요 사실 검사 | 문서·구간·주장·모델의 결합, 미지원 입력 제한 | 자료의 적절성·같은 대상/시점의 지원·반박 여부 |
| 질문 응답 | 허용 claim ID·출처만 표시 | 질문에 맞는 근거 선택, 답변 가능 여부 |

모델이 낸 confidence를 검증된 확률로 취급하지 않는다. 새 모델·NLI·프롬프트만으로 이 판단들이 해결됐다고 가정하지 않는다.
한 번에 여러 층을 바꾼 비교는 어느 변화의 효과인지 분리할 수 없으므로, 변경 항목을 명시하고 인과적 성능 향상을 과장하지 않는다.

원문 구간 선택형 typing은 인용 문자열의 재생성만 없앤다. 모델이 중요한 사실 전제를 처음부터 선택하지 않거나
예측을 사실로 잘못 분류하는 문제까지 코드가 막는 것은 아니다. 실제 Agent의 핵심과 주요 근거를 원문에 대조하는 평가를 유지한다.
현재 고정 Kela 자료3구간은 범용 사실 검색기가 아니므로, 자료 부족으로 보류되는 후보가 많을 수 있다.
이를 해결한다는 이유로 사실 제한을 완화하거나 실패한 전제를 삭제하지 않는다. 자료 검색 범위의 변경도 별도 설계·실험으로 기록한다.

### 이유의 역할과 유형 검사

bounded 구간 선택의 실제 검사에서 원문 도입부가 이유로 선택되고 미래 예측이 필수 사실로 분류됐다.
source→core 지지와 source→reason 지지를 확인해도 reason→core 논거 관계가 성립하는 것은 아니다.
원문에 존재하는 문장을 정확히 복사하는 계약은 이 마지막 관계를 보장하지 않는다.

다음 구현에서는 원문 결합, 핵심에 대한 이유 역할, 사실/가치/예측 유형, 필수 전제 의존성을 별도 출력과 평가 단위로 분리한다.
도입부·재진술·다른 논점·실제 이유를 구분하는 의미 판정은 여전히 모델의 검증 대상이다. 키워드나 문자열 포함만으로 승인하지 않는다.
인용 구간의 포함·중복·원문 위치는 코드로 확인할 수 있지만, 겹친다는 이유만으로 중요한 논거를 자동 삭제하지 않는다.
필수 전제가 불명확하거나 역할·유형이 충돌하면 보류하며, 사실 실패 후 이유를 없애거나 가치로 바꾸는 우회는 유지해서 금지한다.

이 역할 검사는 아직 구현·실행하지 않았다. 고정된 후보와 원문을 재사용해 한 경계씩 검사하고, 산출물 전체를 평가한다.
새 의미 단계의 효과와 호출 비용을 같이 기록하며 현재 형식 계약의 성공을 의미 품질 향상으로 과장하지 않는다.

## 비용과 반복 제한

전체 fresh 실행은 로딩·임베딩·분석·사실 자료 처리·조립을 포함한3600초 deadline을 공유한다. 각 단계가 따로1시간을 갖지 않는다.
새 추론은 기존8시간 ledger를 사용하고 실패·중단 비용을 유지한다. 원문별 분석 cache와 후보별 sparse 비교로 중복 호출을 줄인다.
단계별 시간 예약, 최대 처리 수·비교 수·토큰 수는 준비 manifest에 먼저 고정한다. 예산 때문에 생긴 누락은 성능 평가에서 숨기지 않는다.
현재 자료만으로999개 전부의 의미 분석이1시간에 가능하다고 보장하지 않는다. 실제 처리량·미처리량과 함께 측정한다.

cached runner0.4의 이어가기는 종료된0.3 실행에만 적용한다. 요청 순서·원시 응답·ledger·배포·의미 코드를 결합하고,
오류를 포함한 모든 시도 결과를 재사용한다. 아직 시작하지 않은 호출만 추가하며 미완료 예약은 묵시적으로 재시도하지 않는다.
이어가기의 시간은 앞 실행과 함께 보고하고 fresh 실행의 시간 제한이나8시간 누적 예산을 초기화하지 않는다.

프롬프트는 한 기준선 실행 동안 동결한다. 오류마다 단어 예외·지침·감사 모델을 덧붙이지 않는다.
실패하면 원문 해석, 후보 검색, 집계, 사실 입력, 답변 중 어느 단계가 제품 오류를 만들었는지 먼저 분류한다.
정책 변경, 알고리즘 변경, 모델/프롬프트 변경은 별도 기록으로 구분하고 기존 자체 반복 한도를 임의로 초기화하지 않는다.

## Goal 작업 순서

첫 medoid 기준선의 실제 실패 후, 같은 단위·묶음 안에서 NLI가 대안 target을 순위화하는 제한된 비교를 추가했다.
`target_ranking`은 동일 댓글의 점수를 최댓값 하나로 집계하고 자기 댓글의 점수는 제외한다. `.8`은 기존 순위 기준이지
가입 승인 확률이 아니다. 최대24단위/묶음,1000쌍/실행, 대안1개/묶음이며 초과는 미처리로 기록한다.
대안도 기존 원문 membership을 거친 뒤 지지 수로 비교하고, 동률은 baseline을 유지한다. 핵심 문장은 기존 단위에서만 선택한다.
실제 비교에서 지지3개 이상 후보2→3은 관측됐지만 의미 품질과 Agent 생성 성공은 아직 아니다.
다음 변경은 이유 문장 생성 대신 기존 구간 ID 선택이며, 두 변경의 효과를 분리한다.

1. **평가 상태 분리:** 관계 목표 충족, 통합 실행 완료, 제품 승인, 논문용 검증을 별도로 표현한다. 기존 실패를 지우지 않는다.
2. **원문 분석 adapter:** 기존 계약과 cached 로컬 모델을 연결하고 제한·coverage·단계 예산을 구현한다. 공개 합성 fixture로 계약부터 검사한다.
3. **관점 구조 연결:** 공통 입장과 이유·조건·출처 집계를 실제 산출물에 연결한다. 후보 요약을 자동 지지 근거로 사용하지 않는다.
4. **통합 실행:** 사전 고정한 설정으로 실제 영상의 자동 산출물을 만든다. 관계 목표 미달은 진단으로 보고하되 제품 검사를 생략하지 않는다.
5. **제품 검증:** 자동 노출된 모든 Agent의 핵심·주요 근거, 실제 질문, 비교·후속질문·원문 화면과 시간·누락량을 검사한다.

진행 상태와 증거는 [다음 세션 시작점](NEXT_SESSION.md)에 기록한다. 모델 호출이 없는 설계·코드 테스트를 실제 MVP 작동 증거로 대체하지 않는다.
