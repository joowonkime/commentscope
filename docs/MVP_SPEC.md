# Re.View / CommentScope MVP 명세

버전: `commentscope-mvp-20261110-v36`. 대조 코드: `fff2260`.
상태: 기존 의도·완료 기준을 대조한 기준본. 제품 개발 구현은 [현재 API](PRODUCT_API.md)와 [확인 결과](PRODUCT_DELIVERY_RESULT.md)를 따른다. 후보 설계와 최종 품질 합격은 구별한다.

구현에 필요한 모듈별 계약·알고리즘·API·상태·저장·비용·검증 사례는
[상세 설계](design/README.md), 버전 `commentscope-detailed-design-20261110-v32`에 있다.
현재 구현과 후보 설계의 차이, 실제로 대체할 호출과 유지할 검증을 구별했다.

## 1. 이 문서의 역할과 읽는 순서

이 문서는 제품 의도의 진입점이다. 대화 요약이나 가장 최근 실험이 제품 범위를 바꾸지 않는다.
작업 ID·의존성·구현 상태의 정본은 [추적표](mvp-traceability.json), 작업·재개 절차는
[명세 기반 개발 절차](SPEC_WORKFLOW.md)다. 같은 상태를 날짜별 문서에 복제하지 않는다.

| 판단 대상 | 기준 |
| --- | --- |
| 최신 요청·권한 | 사용자의 명시적 지시. 변경 범위와 근거를 추적표에 반영 |
| 제품 의도·과업·범위 | 이 문서와 연결한 Figma 원본. 화면 예시와 구현 계약은 구별 |
| Factory 합격 기준 | [기존 r5 계약](../tests/fixtures/factory-acceptance-r5.json), [검증 코드](../src/commentscope/factory/acceptance.py) |
| 기존 API | [대화 API](COMPARE_BACKEND_API.md). 아래 후속 계약 제안이 현재 API를 바꾸지 않음 |
| 구현 후보의 상세 계약 | [상세 설계](design/README.md). 원가/품질 채택은 실제 비교·fresh gate와 구별 |
| 구현·다음 작업 | 추적표의 요구사항/작업 ID와 실제 코드·검사 결과 |
| 모델·가격·실행 상태 | 해당 실행의 고정 deployment/plan/장부. 이 문서는 특정 모델을 영구 채택하지 않음 |
| 과거 알고리즘·실험 | 기존 문서와 비공개 원본 보존. 현재 채택·실행 권한의 근거로 승격하지 않음 |

서로 다른 기준이 충돌하면 변경 근거를 먼저 찾는다. 근거 없이 더 최근 파일을 정책으로 채택하지 않는다.
기존 [Factory 실행 명세](MVP_EXECUTION_SPEC.md)의 의미·r5 규칙은 유지한다.
과거 Qwen 설정, 묶음 크기, 타임라인은 현행 deployment·설계 결정으로 다시 확인한다.

## 2. 원래 해결하려는 문제

토론이 많은 YouTube 영상의 시청자가 댓글의 **서로 다른 입장·이유·조건을 이해하고,
직접 질문하며 자신의 생각을 정리하도록 돕는다.** 의견 변화나 설득은 성공 조건이 아니다.
관점은 실제 댓글에서 나온 입장과 출처별 논거다. 재미있는 대립 구도나 인물을 만들어내지 않는다.

팀 [Figma Deliverable](https://www.figma.com/design/Q5oqIs2ekQIagiboAFX7Qc/MAS?node-id=105-1767)의
Before Use → Explore → Converse → Reflect를 제품 과업의 기준으로 유지한다.
2026-11-05 원본 텍스트·구조를 읽어 대조했다. 이번 명세로 Figma나 완료된 M3 보고서를 수정하지 않았다.

| 과업 | 의도한 동작 | 완료를 확인할 행동 |
| --- | --- | --- |
| Explore | 초기 의견 기록 → 관점 카드 → 내 의견과 공통점·차이·더 생각할 점 확인 | 구체적인 일치·차이·조건을 설명하고 해당 근거로 이동 |
| Converse | 1:1 질문 또는 여러 관점의 그룹 대화, 후속 질문·근거 확인 | 답변을 해당 관점·원문과 연결해 이해 |
| Reflect | 초기/현재 의견·이전 대화를 보고 유지·변화·새로 배운 점·추가 고민 정리·저장 | 유지된 의견을 포함해 자기 해석을 남기고 관련 대화를 확인 |

원본 비교 화면은 [210:864](https://www.figma.com/design/Q5oqIs2ekQIagiboAFX7Qc/MAS?node-id=210-864),
그룹은 [378:1866](https://www.figma.com/design/Q5oqIs2ekQIagiboAFX7Qc/MAS?node-id=378-1866),
성찰 입력/분석은 [241:327](https://www.figma.com/design/Q5oqIs2ekQIagiboAFX7Qc/MAS?node-id=241-327)과
[242:404](https://www.figma.com/design/Q5oqIs2ekQIagiboAFX7Qc/MAS?node-id=242-404)다.
그룹 대화는 Converse의 대안 경로다. 3-Agent 화면을 새 Factory 최소 3-Agent 합격 기준으로 바꾸지 않는다.
5개 관점·5% 문턱·1,217/1,130 댓글은 시나리오 예시이며 고정 알고리즘 상수·실측 성능이 아니다.

## 3. 범위와 현재 상태

현재 우선순위는 **선정 영상에서 근거 있는 다양한 관점 발굴 → Agent 생성 완주 → 세 과업 반복 검증**이다.
사용자는 TA용 선정 영상 사전 분석과 저장 Agent 이용을 승인했고, 노이즈 전수 분류보다 관점 발굴을 우선했다.
현재 구현과 새 후보별 선택 검증·root/reply 검색·2천~3천 규모 계약은
[발굴 중심 설계](design/PREPARED_VIDEO_MINING.md)에 구별한다. TASK-018은 무료 계약/구현부터 진행하며
전체 r5와 기존 돈/시간/admission 경계를 변경하지 않는다. 미평가를 비지지나 전반 점유율로 바꾸지 않는다.
사용자가 별도 팀 프론트는 아직 없다고 확인했다. 이미 구현한 제품 API/개발 화면으로 생성 결과를 확인한다.
관점·Agent 품질/원가와 최종 G1~G4 검증은 유지하며 기능 개발을999개 합격 이후로 미루지 않는다.
새 의미 역할 교체는 보류하고 [제품 구현 경로](design/PRODUCT_DELIVERY.md)를 따른다.
Factory 완료와 전체 MVP 완료를 별도로 판정한다. 두 Agent 동일 질문 API로 그룹 토론·성찰을 대체하지 않는다.

| 요구사항 | 현재 구현에서 확인한 범위 | 남은 증거/구현 |
| --- | --- | --- |
| REQ-001 원문·문맥 | 원문·부모·canonical ID·구간 검증 코드 | 현재 자동 산출물의 전수 품질 |
| REQ-002 관점 발견·집계 | 자동 후보/병합/지지/논거 파이프라인 | 현행 설정의 G1~G4 품질·처리 비용 |
| REQ-003 Agent 생성 | bundle 구성·검사·runtime 로딩 경로 | 모든 자동 산출 Agent의 내용·사실·실행 검증 |
| REQ-004 Explore 비교 | 초기 의견과 관점의 비교 API/개발 화면·제한된 실제 응답 | 실제 댓글의 비교 품질·사용자 검증 |
| REQ-005 1:1·근거 | 기존 동일 질문 API와 신규1:1 후속 질문·분리된 이력·원문 조회 | 일반 질문의 답변 적절성 |
| REQ-006 그룹 대화 | Controller·상호 응답·중단/개입 API와 개발 화면 | 실제 댓글의 응답 적절성 |
| REQ-007 Reflect | 네 범주 분석·대화 연결·수정·저장 API와 개발 화면 | 사용자 의미 해석 검증 |
| REQ-008 비용·복구 | 공유 예산·요청 예약·정산·재개·가격 상한 코드 | 서비스 단가·캐시·증분 정책의 검증 |
| REQ-009 제품 통합 | 세 과업의 개발 화면·자동 생성된 합성자료 bundle·실제 모델 응답 | 실제 댓글 품질·사용자 검증·지속 배포 URL |
| REQ-010 증거·의사결정 | 고정 평가·실행 원본·CI 존재 | 명세와 작업의 지속적인 연결·동기화 |

이 표는 점수가 아니다. 부분 구현은 전체 검증 완료를 뜻하지 않는다.
현재 저장소만 받아서는 비공개 원문·장부·실험 결과까지 재현되지 않는다.

## 4. 역할과 정보 경계

다음은 책임 경계다. 역할 하나를 모델 호출 하나로 구현해야 한다는 뜻이 아니다.
책임을 합치는 변경은 입력·판정 독립성·비용·품질 영향을 먼저 명시한다.

| 책임 | 입력 → 출력 | 지켜야 할 경계 |
| --- | --- | --- |
| Source Registry | snapshot → 원문·부모·ID·hash·사용기한 | 원문 불변, 중복과 부모를 독립 지지로 세지 않음 |
| Discovery | 원문·문맥 → 후보 주장·필수 조건·근거 구간·보류 | 인용·반대·미결정을 작성자의 찬성으로 바꾸지 않음 |
| Consolidation / Membership | 후보·원문 관계 → 병합 근거·지지/조건부/반대/불확실/미평가 | 유사도는 검색용, 의미 동치·실제 지지의 대체물이 아님 |
| Source Arguments / Facts | 지지 원문·후보·외부 자료 → 출처별 이유·조건·사실 의존성 | A의 이유를 전체 군집에 전파하지 않으며 사실 확인과 의견 지지를 분리 |
| Agent Compiler | 검증 기록 → 입장·허용 주장·인용·보류 사유를 가진 bundle | 지지 3개만으로 승인하지 않음, 실패한 필수 전제를 삭제해 구제하지 않음 |
| Perspective Runtime | 자기 bundle·질문·이력 → 허용 답변/보류·인용 | 다른 Agent 발언은 대화 문맥이며 자기 원문의 근거로 승격하지 않음 |
| Conversation Controller | 참여자·턴·사용자 개입·실행 한도 → 다음 실행·상태 | 누가 말할지 제어하며 관점·사실을 만들어내지 않음. 세부 프로토콜은 제안 단계 |
| Explore / Reflection | 사용자 원문·관점/대화 참조 → 비교 항목·성찰 기록 | 사용자 의견을 댓글 지지 수에 넣지 않고 의견의 정답을 채점하지 않음 |
| Validation / Execution | 결과·원문·고정 기준·장부 → 오류·승인 범위·중단/재개 | 모델 자체검사·CI·독립 평가·제품 완료를 구별 |

온라인 Auditor라는 이름만으로 추가 유료 검사를 매 턴 넣지 않는다. 기존 host 검증과 생성 전 검사를
유지하며, 별도 온라인 수정 루프의 필요성과 책임은 DEC-004에서 결정한다.

관점 수가 미정일 때의 현재 구조와 추천 변경은 [Factory 구조 정본](design/FACTORY_STRUCTURE.md)을 먼저 읽는다.
DEC-009는 신규 발견/Jev 배정의 제안이며 구조v1의 책임이나 실행 권한을 변경하지 않는다.

모델 호출은 [Decision 계층 상세 설계](design/DECISION_LAYERS.md)의 입력·출력·권한별로 배정한다.
생성·원문 관측·관계·논거·근거 기반 사실 검사와 host 승인을 구별한다. Jev의 논거 component와 raw M1 제한시험은 각각 그 검증 범위에 한정되고,
현재 shared 원격 실행의 기본값은 Sol이다. Jev raw membership은
[M1 opt-in 계약](design/JEV_MEMBERSHIP.md)으로 구현·제한 비교하며 production 채택은 DEC-009의 제안 상태다.
기본 단일 deployment는 유지하며 opt-in 전제 관측 연결의 구현·검증은 [연결 계약](design/JEV_AUDIT_INTEGRATION.md)으로 구별한다.
이 연결은 전체 역할별 배정이나 production Jev 채택을 뜻하지 않는다.
과제별 registry/transport·확률 정책·오류·예산·채택 증거는 DEC-007에서 추적한다.

## 5. 제품 기능의 후속 입출력 계약 — 제안

이 절의 제품 계약은 `/api/v1` 개발 구현에 연결됐다. 현재 필드/미구현 차이는 [현재 API](PRODUCT_API.md)를 따른다. 후속 후보 필드가 모두 구현됐다고 해석하지 않는다.
확정 시 DEC와 작업 ID를 갱신하고 API 명세·부정 사례부터 수정한다.

### Explore — REQ-004

- 입력: 원문 그대로 저장한 초기 의견과 revision, 검증 bundle/perspective ID.
- 출력: 공통점·차이점·추가 고려 질문. 각 비교는 사용자 구간과 허용 claim ID를 참조한다.
- 관점에서 확인되지 않는 내용은 차이라고 단정하지 않고 비교 불가로 표시한다.
- 반대되는 관점을 반드시 만들지 않는다. 더 생각할 점은 정답 교정이나 설득 지시가 아니다.
- 초기 의견 수정 시 이전 비교를 새 의견의 결과로 재사용하지 않는다.

### Converse — REQ-005 / REQ-006

- 현재 계약: `POST /api/session`, `POST /api/ask`, `GET /api/state`, `POST /api/source`를 유지한다.
  초기 의견은 최대 500 Unicode code points, 선택 Agent는 0~2개다. 이 제한은 현행 API 사실이지 제품의 영구 상한이 아니다.
- 그룹 제안 입력: bundle revision, 참여 Agent IDs, opening question, 선택된 대화 턴.
- Controller 제안 상태: 준비·응답 중·사용자 개입 대기·종료·오류. 상호 응답, 중단/재개,
  턴 수/출력/비용 한도·부분 실패·중복 요청 규칙을 DEC-002에서 확정한다.
- 출력은 발화자·응답 대상 message ID·인용 source IDs와 연결한다. 다른 발언에 동의해도
  자기 출처가 없으면 새 입장·해결책·사실을 자기 근거로 답하지 않는다.
- 실제 적격 Agent가 2개뿐이면 3번째를 합성하지 않는다. 가용 상태를 표시하고 대체 경로를 유지한다.

### Reflect — REQ-007

- 제안 입력: 초기/현재 의견 revision, 사용자가 참여한 대화의 message IDs, 선택한 관점 참조.
- 제안 출력: 유지·변화·새로 배운 점·추가 고민 목록과 사용자 원문 구간·관련 대화 링크·저장 revision.
- 변화가 없거나 특정 범주가 비어 있어도 유효하다. AI 제안을 사용자가 수정·저장할 수 있어야 한다.
- 관련 대화와 의견 변화의 원인을 구별한다. 대화가 생각을 바꿨다고 근거 없이 단정하지 않는다.
- 사용자 글은 AI 문장으로 덮어쓰지 않는다. 없는 과거 대화나 근거를 연결하지 않는다.
