# MVP를 테스트 기반으로 완성하는 순서

관점 생성→Agent 생성 파이프라인을 먼저 완성하고 프론트엔드를 연결한다.
코드의 CI 통과와 실제 모델의 의미 품질 통과를 각각 확인한다.

## 한 변경의 작업 순서

1. 저장된 실패를 단계별로 모아 공통 원인과 의미 오류를 구분한다. 현재 실패와
   같은 규칙을 사용하는 다른 단계도 함께 확인하고, 합성 사례와 기대 동작을 고정한다.
2. 해당 테스트가 실패하는 것을 확인한 뒤 필요한 코드를 구현한다. 실제 저장
   응답으로 오프라인 회귀를 수행하고 요청 크기와 추가 호출 수도 비교한다.
3. 관련 회귀 검사와 `python tools/check_factory_draft.py`를 통과시킨다.
4. PR에 문제·변경 동작·검증 결과·남은 한계를 기록한다.
5. 자동 병합이 승인된 PR은 `--auto --squash`를 설정한다. 최신 main 기준의
   Ubuntu·Windows 필수 검사가 모두 통과하면 GitHub가 병합한다.
6. 공통 원인의 수정과 오프라인 회귀가 모인 뒤 실제 모델 검증 비용을 산정한다.
   작은 수정마다 전체 유료 게이트를 반복하지 않는다. 제한된 진단과 전체 게이트의
   목적을 구분하고, 기존 고정 품질 기준은 유지한다.

테스트 기대값을 현재 출력에 맞춰 낮추지 않는다. 원문·부모·출처·조건·부정·
논거 귀속을 보존하며, 근거 부족 보류와 실행 실패도 검사한다.
단순한 문서 수정에는 동작을 복제하는 테스트를 추가하지 않는다.

## 이어서 구현할 순서

| 순서 | 필요한 동작 | 완료를 확인할 근거 |
| --- | --- | --- |
| 1 | 공유 API 예산·실행별 한도·중단/재개 | 추론 전 비용 예약, 불명확한 비용 보존, 중복 호출 방지 검사 |
| 2 | 전체 Factory의 OpenRouter 실행 연결 | `openrouter_factory_pipeline`으로 같은 단계·산출물·검토 계약의 G1 실행 |
| 3 | 관점·지지·논거·Agent의 실제 품질 | 새 원격 모델의 G1 전수 검토, 서로 다른 Agent와 고정 질문 |
| 4 | 실제 자료의 처리 규모 확대 | 같은 설정의 G2/G3/G4와 기존 r5 기준 |
| 5 | 검증된 결과와 프론트 연결 | 관점 탐색→질문→근거 조회 및 M4 세 과업의 end-to-end 확인 |

기존 기준은 G2 12/19·G3 45/74 보존, G4 453/755 활용, 집계 지지 전수 유효,
서로 다른 Agent 최소2개·각 유효 지지3개와 사실·내용·실행 검증이다.
원격 개발8건, 모의 응답 테스트, CI 성공만으로 이 기준의 통과를 선언하지 않는다.
자세한 실제 검증 계약은 [재개 계획](FACTORY_RESTART_PLAN.md)을 따른다.

## 비용 검사

유료 요청에는 실행별 한도와 공유 장부를 사용한다.
모델 context 전체와 제공자 가격 상한으로 요청 비용을 먼저 예약하고 실제 응답의
비용으로 정산한다. 비용 누락·전송 중단·상한 초과는 보수적인 금액을 보존하며
장부를 대조하기 전에는 새 유료 요청을 막는다. 총한도·기존 사용액·실행 한도를
재개하면서 변경하지 않는다. 새 계획도 같은 공유 장부에서 비용을 집계한다.

[OpenRouter 검사 안내](OPENROUTER_FACTORY.md)의 공유 비용 정책을 사용한다.
합성·회귀 검사는 네트워크나 유료 API 없이 수행하고, 실제 응답과 실패 기록은
비공개로 유지한다.

저장된 요청·응답과 실행 오류를 함께 점검할 때는 다음 도구를 사용한다.

```bash
python tools/audit_factory_contracts.py \
  --run runs/saved-factory-run \
  --output runs/private-audit/new-report.json
```

`--run`을 반복하면 여러 실행을 함께 검사한다. 원본 실행은 읽기만 하고 새 보고서도
기존 파일을 덮어쓰지 않는다. 키·모델·네트워크 연결은 필요 없다.
보고서에는 원문·생성 문장·검증기 메시지를 복사하지 않는다. 요청 hash를 확인하고,
저장 출력의 스키마 위반과 스키마를 통과했으나 단계별 검증기에서 거부된 오류를
구분한다. 누락된 응답, 생성·전송 오류와 미지원 스키마도 별도로 기록한다.

검사기는 Factory가 사용하는 명시된 스키마 부분집합만 지원한다. 지원하지 않는
키워드를 만나면 검사를 완료했다고 표시하지 않는다. 정규식은 Python 문법을 사용한다.
스키마에 없는 길이·출처·중복·상태 간 규칙은 이 도구가 추론하지 않는다.
이전 검증기의 오류 기록과 대조할 뿐 검증기 자체를 재실행하지도 않는다.
종료 코드0은 보고서를 작성했다는 뜻이며, 발견한 과거 오류의 해결이나 실제 의미 품질
통과를 뜻하지 않는다. 잘못된 요청 hash나 미지원 계약은 종료 코드1로 반환한다.

제공자의 구조화 출력과 별개로 길이·선택 ID·중복·조건 간 관계는 호스트에서 확인한다.
자유 생성 문장, 긴 선택 목록과 중복 상태 필드는 실제로 필요한지 함께 검토한다.
조건·부정·발언자 귀속·가정/현실·예측/사실의 의미 보존은 별도 회귀와 원문 대조가
필요하다. 저장 응답의 오프라인 재검사는 현재 코드의 G1~G4 승인이나 다른 실행의
응답을 공식 검증에 재사용할 권한을 부여하지 않는다.
