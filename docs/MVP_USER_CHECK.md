# MVP 사용자 확인 절차 — 준비본

TASK-012, REQ-009/010. 아직 참여자 평가를 실시하지 않았다. CI·개발자 검토·Figma 완성도와
사용자의 이해 향상은 별개다. 정식 품질을 통과한 고정 분석을 사용하며, 개발용 합성 자료를 실제 댓글로 소개하지 않는다.

## 비교할 과업

같은 영상과 같은 댓글 범위를 사용한다. 원문 목록에는 부모 문맥도 함께 제공하고,
Re.View에는 그 자료에서 자동 생성한 전체 가용 관점을 제공한다. 좋은 Agent만 골라 보여주지 않는다.
처리 범위·분석 revision·자료 사용기한·미검증 범위를 시작 전에 기록한다.

참여자는 먼저 초기 의견을 적고 두 방식을 각각4분씩 사용한다. 절반은 원문 읽기부터,
나머지는 Re.View부터 시작한다. 순서와 두 번째 과업의 학습 효과를 기록한다.
첫 소규모 확인은 결함을 찾는 용도이며 통계적 우월성이나 시장 경쟁력의 증명이 아니다.

1. 댓글의 서로 다른 관점 세 가지를 설명한다. 자료에 세 가지가 없으면 확인한 수와 한계를 적는다.
2. 각 관점의 이유를 말하고, 실제 원문으로 두 사례를 확인한다.
3. 조건·예외·보류 중 한 가지를 찾아 설명한다. 확인하지 못한 부분은 모른다고 표시한다.
4. Re.View에서는 한 관점에 후속 질문을 하고, 가능하면 그룹 대화를 확인한다.
5. 현재 의견과 회고를 저장하고 새로고침 후 다시 연다. 의견 변화가 없어도 성공이다.

## 남길 관측

| 항목 | 기록 기준 |
| --- | --- |
| 관점 구별 | 서로 다른 실제 주장 수와 혼동/누락. 사람이 원문과 대조 |
| 이유 귀속 | 제시한 이유가 해당 작성자·관점의 것인지, 다른 출처에서 옮겼는지 |
| 조건 보존 | 실제 조건을 보존했는지, 무조건 주장으로 바꿨는지 |
| 원문 확인 | 두 출처를 찾는 데 걸린 시간과 잘못 연결한 수 |
| 사용성 | 각 과업 완료/실패·막힌 화면·오류 메시지·완료 시간 |
| 자기 생각 | 유지/변화/새로운 질문을 사용자가 표현했는지. 변화 방향은 채점하지 않음 |
| 비용 | 최초 Factory와 분리한 비교·질문·그룹·회고 실청구, 재열람 신규 호출 수 |

참여자 식별은 임의 번호만 사용한다. 키·세션 token·개인 의견·원문 대화는 공개 Git/PR에 넣지 않는다.
유료 과업은 동결한 공유 장부·실행 상한·기한 안에서만 수행하며, 남은 예산으로 못 하면 미실시로 기록한다.
실패한 과업을 성공한 참여자로 대체하거나 좋은 결과만 합산하지 않는다.

결과에는 방식별 원자료 수·진행 순서·실패·제한을 함께 적는다. 실제 참여자 확인 전까지
‘이해가 향상됐다’, ‘일반 댓글 읽기보다 낫다’, ‘경쟁력이 입증됐다’고 결론 내리지 않는다.
