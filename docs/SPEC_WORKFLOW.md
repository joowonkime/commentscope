# 명세를 기준으로 개발하고 재개하기

이 절차는 대화·요약에만 남은 합의가 다음 작업에서 사라지는 것을 줄이기 위한 저장소 절차다.
Compact의 인과를 입증하거나 모든 도구의 재개 동작을 자동 제어하는 기능은 아니다.

## 시작·Compact·담당자 변경 후

1. `AGENTS.md` → [MVP 명세](MVP_SPEC.md)를 읽는다.
2. `python tools/check_mvp_spec.py --resume`로 명세 버전·다음 작업·요구사항·열린 결정·유료 실행 상태를 확인한다.
3. [추적표](mvp-traceability.json)에서 해당 TASK와 REQ/DEC 본문·`design_refs`를 읽고,
   [상세 설계](design/README.md)의 담당 절과 필요한 기존 계약·코드·실패만 추가로 읽는다.
4. 실제 git 상태·HEAD·진행 프로세스·원본 artifact를 확인한다. 비공개 progress가 없으면 합성 검증부터 가능한 범위를 진행한다.
5. 현재 요청이 저장 명세를 변경하면 변경 범위·근거·미결정 상태를 먼저 기록한다. 대화 요약을 근거로 상태를 추측하지 않는다.

매번 과거 전체 대화를 넣지 않는다. 읽은 명세 버전과 작업 ID를 진행 기록에 남긴다.
검사 성공은 참조·작업 그래프의 정합성 검사이며 명세의 타당성, 실제 원문 품질, 작업 완료를 보증하지 않는다.

## 한 작업의 계약

작업 시작 전 아래 내용을 추적표 또는 연결한 설계 결정에 기록한다.

- TASK ID와 연결한 REQ/DEC IDs, 해결할 일반적인 문제와 제외 범위.
- 선행 작업, 변경할 책임·입출력·오류 상태, 기대하는 산출물.
- 보존해야 할 정상·부정 사례, 기존 구조와 달라지는 점.
- 오프라인 검사와 실제 의미 검증을 구별한 채택/폐기 조건.
- 추론이 필요한 경우 고정 표본·모델/provider·prompt/schema·가격 상한·최대 비용·중단 규칙.

입출력·책임 변경은 명세를 먼저 수정하고 구현한다. 동작 변화 없는 수정도 해당 REQ를 명시하되
불필요한 제품 재설계를 추가하지 않는다. 설계 문구 변경만으로 실제 구현 상태를 올리지 않는다.

## 구현·검증·병합

1. 명세와 정상/부정 기대 동작을 고정한다. 동작 변경에는 의미 있는 실패 재현을 만든다.
2. 필요한 범위만 구현하고 관련 검사·Factory 연결 검사를 수행한다. 문서 수정에 구현을 복제하는 테스트를 추가하지 않는다.
3. 저장된 실패의 오프라인 검사는 현재 fresh 품질 합격과 구별한다. 실제 모델 비교는 동결한 가설·표본·예산 안에서만 수행한다.
4. PR에 REQ/TASK/DEC IDs, 계약 변경 여부, 결과·한계·미실행 검사를 적는다.
5. 사용자에게 이미 승인된 범위의 PR만 기존 자동 병합 정책을 따른다. CI가 제품 범위 변경을 승인하지 않는다.
6. 실제 결과가 나온 범위만 상태에 반영한다. `done`은 명시된 산출물·검증 증거와 완료된 선행 작업을 필요로 한다.

[TDD 절차](MVP_TDD.md)는 이 순서 안에서 코드 회귀를 담당한다. 의미 품질은 고정 평가와 원문 대조로,
전체 제품 완료는 세 과업의 end-to-end 동작으로 별도 확인한다.

## 변경 결정 기록

결정마다 `DEC ID / open·proposed·accepted·rejected / 근거 / 영향 REQ / 대안 / 검증·비용`을 기록한다.
현재 미결정의 상세 설계는 DEC에 연결한 문서에서 작성하고 수락 상태를 명시한다.
기존 사용자 의도와 r5·활성 금융 권한은 구현 편의를 위해 조정하지 않는다.
사용자가 승인한 팀 한도$150 증액(DEC-011), 기존 운영장부$50, 이전 owner$8·소규모 추가검증$3,
현재 [전체 댓글 풀 검증](design/WIDE_MINING_EXPERIMENT.md)의 추가상한$15(DEC-012)을 구별하며,
과거 plan/장부를 새 한도로 다시 만들거나 이전 차감을 초기화하지 않는다.
가설의 결과가 나쁘면 실패와 비용을 보존하고 폐기한다. 다른 이름의 새 실험으로 예산을 초기화하지 않는다.

명세·작업 그래프를 바꾸면 `spec_version`을 갱신하고 이유를 남긴다. 과거 baseline commit과 검사 결과를
현재 결과로 덮어쓰지 않는다. 새로운 코드 commit에 대해 증거의 유효 범위를 다시 확인한다.

## 상태의 의미

요구사항 구현 상태는 `not_implemented / partial / implemented`다. 이는 품질 상태가 아니다.
검증은 증거마다 `kind / scope / reference / result`를 기록한다.
`code`는 파일 존재·구현 범위, `offline`은 모의/회귀, `limited_live`는 제한된 모델 실행,
`formal_gate`는 해당 고정 gate, `product_e2e`는 제품 과업의 검증이다.
하나의 증거가 다른 종류의 검증을 대신하지 않는다.

작업 상태는 `todo / next / in_progress / done / deferred`다.
`next`는 한 개이며 명세 검사에서 의존성을 확인한다. 실행 중이면 그 작업의 상태를 `in_progress`로 바꾸고
`resume.next_task`는 같은 ID를 유지한다. 원인 분석·비용 보류는 실패 결과와 별도 기록한다.
유료 실행 대기 중 독립된 제품 작업을 진행하면 `resume.parallel_tasks`에 그 작업 ID를 명시한다.
모든 활성 작업을 정본에 기록하며 각각의 선행 완료 조건을 유지한다. 주 작업과 부수 작업의 품질 증거를 합치지 않는다.

## 중단 전 인계

추적표에 다음 작업과 미결정을 갱신하고, 개인 실행 기록에는 아래 내용을 저장한다.
실제 원문·키·개인 대화·장부는 공개 명세나 PR에 복사하지 않는다.

```text
spec_version / TASK ID / 현재 코드 HEAD와 branch
완료한 범위와 증거 종류 / 아직 해결되지 않은 실패
진행 중인 실제 handle 또는 없음 / 미확정 과금 유무
다음에 할 단일 작업 / 실행 전 읽을 REQ·DEC·artifact
이번 변경의 비용과 전체 예산 상태(관측 시각 포함)
```

공유 명세와 현재 실제 상태가 다르면 정정한 뒤 재개한다. 간단한 질문에 답하거나 읽기만 한 것을
대량 실험 재개 지시로 해석하지 않는다. 추가 설명이 필요하면 독립적으로 할 수 있는 오프라인 작업을 먼저 마친다.
