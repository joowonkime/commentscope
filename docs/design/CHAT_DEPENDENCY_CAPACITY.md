# Jev와 Sol 논거 요청의 용량 책임 분리

TASK-018 / REQ-001·003·008·010. 무료 회귀 수정이며 새 모델 실행은 없다.

999 개발 실행에서 Sol의 enum JSON 논거 요청을 만드는 `chat_requests`가 먼저
Jev `requests`의28000바이트 제한을 검사해 원문4개가 보류됐다.
원 실행 결과와 코드·manifest는 별도 worktree에 그대로 보존한다.

공통 질문 구성은 원문·부모·전체 단위·질문·선택지와 순서를 유지한다. 구조 검사는 공유하되
Jev의 실제 전송 경로는 기존 모델/provider·최대16질문·28000바이트 검사를 계속 통과해야 한다.
Sol chat 변환에는 Jev 전송 바이트 제한을 적용하지 않고 실제 Sol 요청의 전체 payload를
기존 `Client.measure`/WireBudget/dispatch에서 검사한다. 원문을 자르거나 질문을 생략하지 않는다.
응답 결합은 해당 경로의 원 요청을 다시 만들고 모델/provider·영수증·전체 질문 응답을 검증한다.
돈·시간·source/condition/owner/fact·최소지지·Agent 기준을 바꾸지 않는다.

회귀는 작은 입력의 기존 chat 요청 동일성, Jev 상한을 넘지만 Sol에 맞는 전체 원문,
Jev의 초과 요청 거부, 실제 Sol 용량 초과 거부, 변조/누락 응답과 기존 의미 veto를 검사한다.
이 수정으로 실제 Agent가 늘었다고 주장하지 않는다. 다음 실제 검증에는 새 코드에 맞는
고정 계획·가격·예산·기한이 필요하며 완료된999실험을 새 결과로 재분류하지 않는다.

이 결과는4원문이 최종 의미 검증을 통과한다거나 Agent가 늘었다는 증거가 아니다.

## 별도로 남은 해석·검증 설계

현재 경로는 Jev M1 외에 Sol의 독립 M2·유형/귀속·의존 관계·충실도 검증이 있다.
이번 실험만으로 Jev 모델 하나가 전체 실패 원인이라는 결론을 내리지 않는다.
복합 원문의 가치·예측·희망을 한 고정 단위로 판정하는 문제, 조건/발언자 보존,
불확실성의 후보별 영향 범위는 이 전송 수정과 별도다. 검증 횟수를 늘린 개선도 입증하지 않았다.
후속 설계는 정확한 원문 구간 분해→관계 판정→독립 조건/귀속/필수 근거 검증의 입력·책임·
실패 범위를 구체화하고, 올바른 조건 보류와 불필요한 소실을 구별하는 합성/원문 기준부터 고정한다.
새 역할·추가 모델 호출·반복 판정은 아직 채택하거나 실행하지 않았다.
