# 영상 성격별 후보 선정과 MVP QA

TASK-012 준비 / TASK-022 / REQ-001·002·003·005·009·010.
2026-11-13 KST의 탐색 결과다. 사용자는 영어/한국어 모두 허용하며 건설적인 토의와
TA의 초행·시나리오 이탈 평가를 고려한 영상 선정을 요청했다.
이 문서는 우리의 사전 QA 계획이며 TA의 공식 세부 채점표가 아니다.

**추천은 영어 CNBC 주4일제를 첫 기능 검증 대상으로, 한국어 SBS 주4일제/임금을 조건·언어·규모
검증 대상으로 나누는 것이다.** 댓글 수가 많은 영상 하나에 모든 검증을 맡기지 않는다.
내용 적합성의 예비 후보이며 자동 Agent 생성·품질 합격이나 실제 사용성 성공은 아직 검증하지 않았다.

## 선정 기준

건설적 토의는 댓글 수나 논쟁 강도가 아니라 작성자가 입장에 이유·조건을 붙이고,
다른 주장에 구체적으로 응답하거나 자기 경험의 범위를 밝히는 사례로 판단한다.
다른 의견이 반드시 정반대여야 하는 것은 아니다. 같은 찬성이라도 적용 조건/이유의 차이를
보여줄 수 있어야 한다. 욕설·인물 평가·응원만으로 다른 관점을 만들지 않는다.

- 첫 기능 검증용: 실제 댓글에서 구별할 논점과 설명할 이유/조건이 보이고 토론 가능한 문장이 있는가.
- Agent 자격: 기존 최소2관점·각3유효지지·출처/조건/필수 사실/실행 검사를 유지한다.
  예비 검토에서 몇 종류가 보였다고 그 수의 군집이나 Agent를 강제하지 않는다.
- 규모 검증용: 실제 회수 가능한 댓글이2천~3천 개에 이르는지 별도로 확인한다.
  표시 댓글 수에는 답글이 포함되며 실제 회수 가능 수와 같다고 가정하지 않는다.
- 영상의 말과 댓글 작성자의 말을 구별한다. 영상에서 양측을 소개해도 댓글이 양쪽으로 나뉜다는 뜻은 아니다.
- 정상 사례와 편향·부족·어려운 실패 사례를 함께 유지한다. 기존 UBI 고정999/r5 평가를 새 영상으로 교체하지 않는다.

## 주4일제에서 실제로 드러난 구별점

CNBC 표본에는4일×10시간 근무로 긴 주말을 확보하는 경험과,32시간 근무를 말하는 답글이
같은 thread에 있다. 둘 다 주4일이라는 이유로 같은 조건의 지지로 묶으면 안 된다.
유연한 시간 배분이 고정된4일제보다 낫다는 제안과, 고객 대응/물류가 필요한 업종의 적용 한계를
설명하는 댓글도 있다. 이 구별점들은 후보 메모이며 자동 군집의 정답 수를 미리 정한 것이 아니다.

SBS 표본에는 임금을 일부 포기하고 휴식/육아 시간을 택하고 싶다는 주장과,
그 삭감 비율이 공정해야 한다는 주장, 현재 주5일조차 보장되지 않으니 준수가 먼저라는 주장이 있다.
주5일 준수 우선을 주4일 반대로, 주1일 출근+4일 재택을 주4일 근무로 바꾸면 오류다.
논거가 존재하더라도 비방 표현·미확인 수치·개인 경험을 검증된 일반 사실로 승격하지 않는다.

입장·왜/어떤 조건·실제 반론·원문 확인을 서로 다른 표현으로 질문하고 핵심 과업을 막는 실패를 기록한다.
[기존 사용자 확인 절차](../MVP_USER_CHECK.md)의 Explore→Converse→Reflect와 연결하되
사용자 이해 향상/독립 평가/TA 통과 여부는 실제 참여자 결과가 나올 때까지 미검증이다.

## 수행한 범위와 다음 확인

공식 API로16개 영상 메타데이터와8개 영상의 관련성순/최신순 첫 페이지를 조회했다.
유일 root 수는 CNBC 주4일제190, SBS197, 팁192, 재택190, TED170, DW180,
MBC 클립58·141이다. root의 parent 관계와 반환된 inline reply를 보존했다.
CNBC의32/40시간 정정 thread10답글과 SBS 선택/육아 thread34답글은 별도로 한 페이지 전체를 받았다.
많은 다른 thread의 inline reply는 일부뿐이며 전체 답글을 검토했다고 주장하지 않는다.
선택한 논거/조건 사례를 정성 검토했으며 전체 수집 표본의 전수 의미 채점은 하지 않았다.

총27개 공식 API 읽기 요청, **OpenRouter/새 embedding/Agent 생성 호출0**이다.
원자료·댓글 ID·요청별 hash와 사례 참조는 비공개 실행 자료에 보존한다. 댓글·키를 Git에 넣지 않는다.

후속은 우선 두 주4일제 영상에서 기존 최소 지지와 이유/조건을 충족할 실제 출처를 대조하고,
범위·배정·예산·정상/실패 사례를 고정한 뒤 같은 파이프라인으로 비교하는 것이다.
영상별 snapshot/관점/대화를 분리하고 서로 다른 영상의 댓글을 합쳐 최소 지지를 채우지 않는다.
이미 읽어 본 수정용 사례와 확인용 표본을 구별하며 질문 표현도 바꿔 같은 문항에만 맞추지 않는다.
내용이 좋아 보인다는 이유로 즉시 전체3천 개 유료 분석을 시작하지 않는다.
서로 다른 원인인 영상 특성·언어·표본 규모·코드 변경을 한 번에 바꿔 개선 원인으로 보고하지 않는다.

이번 탐색은 원UBI에서 확인한 원문 해석/검증 손실을 해결한 결과가 아니다.
선정 영상을 준비하는 제품 경로와 기존 전체 r5·999 평가를 유지하며,
실제로 기능이 나오는지 확인한 영상만 준비 상태로 승격한다. 현재 후보는 아직 그 상태가 아니다.

새 주제의 필수 실증 사실을 검사하려면 그 주제에 맞는 외부 문서가 필요하다.
직전 실행에 공급한 Kela UBI 자료만으로 주4일제의 생산성/임금 효과를 확인할 수 있다고 가정하지 않는다.
문서가 부족하면 보류하고, 필수 사실을 삭제하거나 의견/예측으로 바꿔 Agent를 승인하지 않는다.
